# Oracle / Deployer Key — How It's Held (no secrets below)

1. **Not in this app.** This project's `.env` / `.env.example` hold no raw key or mnemonic — only Circle vars (`CIRCLE_API_KEY`, `CIRCLE_ENTITY_SECRET`, `AGENT_WALLET_ID`, `AGENT_WALLET_ADDRESS`, `AGENT_ID`) + `ANTHROPIC_API_KEY` / `VITE_CLIENT_*`. No `PRIVATE_KEY`/`DEPLOYER_KEY`/`ORACLE_KEY`/`MNEMONIC`.
2. **The oracle `0xd87f530b…05c` is a plain EOA**, not a Circle wallet. Its raw private key lives as `PRIVATE_KEY` in the separate contracts repo `~/tikpema/tikpema-contracts/.env` (confirmed: that key derives to `0xd87f530b…05c`). It is `owner = oracle = treasury` of `TikpemaPrediction` @ `0xf38492403ce3f1c94ef6322b78c9024d26ed87e1`.
3. **Prior usage = Foundry from that repo:** deployed via `forge script script/Deploy.s.sol` (`vm.envUint("PRIVATE_KEY")`); admin/resolve done with `cast send … --private-key $PRIVATE_KEY`. So `resolveMarket` has so far been signed by that local EOA key, not by Circle.
4. **The agent betting wallet (`AGENT_WALLET_ADDRESS`) is a DIFFERENT address** — a Circle dev-controlled wallet, signed via `initiateDeveloperControlledWalletsClient` + `createContractExecutionTransaction` (`predict-bet.mjs`/`_circle.mjs`). It is **not** the oracle, so the existing Circle signing plane cannot resolve markets as-is.
5. **To sign `resolveMarket` from the server:** load the oracle EOA `PRIVATE_KEY` into a viem `walletClient` (`privateKeyToAccount`) on Arc and call `resolveMarket(marketId, yesWon)`, paying USDC gas from that EOA. (Alternative, out of scope: `setOracle(AGENT_WALLET)` to route resolution through the existing Circle dev-controlled plane.) Move the key into this app's server env (never `VITE_`-prefixed) — do not commit it; `.env` is already gitignored.
